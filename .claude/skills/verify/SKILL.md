# Верификация результата

> **Принцип:** изоляция контекста — суб-агент проверяет результат по эталону, **не видя** истории его создания. Иначе он якорится на рассуждениях автора и подтверждает их вместо проверки.
> Архитектурное решение проверяется через `/archgate`, не здесь.

Аргументы: $ARGUMENTS

## Шаг 0. Тип проверки

| Аргумент | Что проверяет |
|---|---|
| `code` | Качество кода: логика, краевые случаи, безопасность, связность. Скрипты vault и код рабочих репозиториев (натравить на `git diff`) |
| `task` | Приёмка: артефакт против DoD из карточки задачи |
| `chain` | Поток данных: прочитаны ли потребители изменённого? совпадают ли контракты? |
| `premortem` | Границы и предвзятость: scope от анализа или подгонки? что не прочитано? где сломается в проде? |
| `auto` / пусто | автоопределение: `.py/.ts/.sh/.tf/.yaml` → code; тикет → task; >1 компонента → предложить chain; после фикса → предложить premortem |

## Шаг 1. Собрать вход (оркестратор)

- **code:** `git diff` (или указанные файлы) + конвенции затронутого репозитория (`CLAUDE.md`, линтер, соседний код) + чеклист.
- **task:** карточка `10-governance/tasks/<ticket>.md` (DoD + поле `artifact`) + сам артефакт. Глубина по `verification_class`: `trivial` — проверки не требует; `closed-loop` — сверка с критерием; `open-loop` — проверка допущений, а не исхода; `problem-framing` — проверка рамки, а не решения.
- **chain:** `git diff` + поиск всех потребителей изменённых функций и выходов + прочитать каждого.
- **premortem:** `git diff` + список файлов, которые автор НЕ читал, но которые могут быть затронуты + постановка задачи.

## Шаг 2. Запустить суб-агента

Спавнить с входом из шага 1. Суб-агент **не получает** историю сессии, задание автора и промежуточные рассуждения — только артефакт, эталон и чеклист.

**Эталон:** code → конвенции репозитория; task → DoD карточки; chain и premortem → сам код. **Эталон не определяется → СТОП:** «нужен рецензент, а не верификатор» — это разные роли, и подменять первую второй бессмысленно.

**Чеклисты:**
- **code:** логика верна? краевые случаи? секреты, персональные данные, инъекции? связность (что придётся менять вместе)? тест проверяет наблюдаемый результат, а не факт запуска?
- **chain:** (1) кто потребляет каждый изменённый выход? (2) прочитан ли каждый? (3) типы и формат совпадают? (4) переменные и окружение определены в нужной области? (5) контракт не сломан?
- **premortem:** (1) scope от анализа или подгонки под заранее выбранный вывод? (2) что не прочитано, но затронуто? (3) предположи, что это сломалось в проде — назови три причины; (4) какие есть альтернативные объяснения исходной проблемы? (5) заявленный объём («один файл», «простой фикс») равен реальному?

## Шаг 3. Вердикт

Суб-агент возвращает:
- **PASS** (0 критических, 0 высоких) / **CONDITIONAL** (0 критических, ≥1 высокое) / **FAIL** (≥1 критическое).
- Таблица несоответствий: важность · файл · строка · что · почему · эталон.
- Сводка и рекомендация в 1–3 предложения.

## Шаг 4. Показать

Вывести вердикт. Дальше решает инженер: принять, исправить или отклонить вердикт с аргументом. **Спорный вердикт не продавливать** — верификатор ошибается тоже, и его ошибка дешевле, чем привычка не спорить с ним.
