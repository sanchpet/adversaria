# /skill-add — затащить чужой скилл или плагин

Источник: $ARGUMENTS

Чужой скилл — это **чужой код в твоём агенте**, исполняемый с твоими правами и в твоём контексте. На рабочем контуре это ещё и код, который увидит рабочие данные. Порядок ниже про две вещи: не установить лишнего и не завести копию, которую потом обновлять руками.

> Тонкий скилл. Изменение окружения вообще — `/env`; оценка архитектурного решения — `/archgate`.

## Шаг 1. Классифицировать источник

Смотреть в дерево репозитория **до** клонирования:

```sh
gh api 'repos/<owner>/<repo>/git/trees/HEAD?recursive=1' --jq '.tree[].path'
```

(кавычки обязательны — `?` съест shell)

| Что видно в дереве | Что это | Как ставится |
|---|---|---|
| `.claude-plugin/marketplace.json` | **маркетплейс** (может нести несколько плагинов) | `claude plugin marketplace add` → `install` |
| `.claude-plugin/plugin.json` без marketplace | плагин внутри чужого маркетплейса | `claude plugin install <plugin>@<marketplace>` |
| только `SKILL.md` | голый скилл — **апстрим-канала обновления нет** | см. шаг 4 |

## Шаг 2. Разведка — прочитать ДО установки (БЛОКИРУЮЩЕЕ)

Читать через API, не клонируя:

```sh
gh api repos/<owner>/<repo>/contents/<path> --jq .content | base64 -d
```

1. **`description` во frontmatter — это триггер-поверхность.** Скилл вызывается моделью: он включается сам, когда контекст подходит под описание. Разговорные формулировки означают, что режим может встать без твоей команды. Проговорить владельцу **фактические** триггеры, а не заявленные в README.
2. **Инструкции на самозакрепление** — «активен каждый ответ», «сомневаешься — активен», отсутствие условия выключения. Такой скилл переживает свою задачу и конкурирует с конвенциями из `CLAUDE.md`.
3. **Хуки, MCP-серверы, суб-агенты, `allowed-tools`** — исполняемая поверхность. Хук выполняется без твоего решения; MCP-сервер поднимает процесс и ходит в сеть.
4. **Запрос учётных данных, чтение вне репозитория, сетевые вызовы** в теле скилла.
5. **Лицензия и автор.**

**Вето — ставить только через `/archgate` и с явным решением владельца:** хуки, MCP-серверы, любой доступ к секретам, отсутствие лицензии.

**Отдельно для рабочего контура.** Скилл, который ходит в сеть или в MCP, на рабочей машине отправляет наружу рабочий контекст. Это вопрос политики работодателя, а не вкуса: если она запрещает передачу рабочих данных сторонним сервисам, такой скилл не ставится вовсе — и обсуждать тут нечего.

## Шаг 3. Выбрать дом

Вопрос не «куда положить копию», а **нужна ли копия вообще**. По умолчанию — не нужна.

| Дом | Когда | Обновление |
|---|---|---|
| **нативно, `--scope user`** (умолчание) | проба, личное использование, всё чужое | `claude plugin update` — тянет апстрим |
| **нативно, `--scope project`** | нужен всем в конкретном репозитории, объявляется в его settings | то же |
| **dotfiles** | нужна воспроизводимость на другой машине | через `/env` |
| **вендоринг в `.claude/skills/` этого vault** | **почти никогда для чужого** | руками, навсегда |

Вендоринг чужого скилла оправдан ровно в одном случае: он становится **глаголом самой системы** (как `/open`, `/task`) и ты принимаешь авторство. Иначе это форк без апстрима — балласт по INV-3 и размытая writer-ownership (INV-19).

**Скоуп по смыслу, не по удобству:** скилл про предмет этого vault — сюда; скилл про окружение и тон — user-level, он нужен во всех репозиториях, а не только там, где случайно поставлен.

## Шаг 4. Поставить

```sh
claude plugin marketplace add <owner>/<repo>     # --scope user|project|local
claude plugin install <plugin>@<marketplace>     # --scope user по умолчанию
```

**Голый скилл (без манифеста):** апстрим-канала нет. Либо форкнуть себе и тянуть из форка осознанным мержем, либо положить в `~/.claude/skills/<name>/` и принять, что обновление ручное. Скелет своего — `claude plugin init <name>`. Выбор **проговорить владельцу**, не решать молча.

## Шаг 5. Проверить

- **Состояние плагинов лежит в `$CLAUDE_CONFIG_DIR`, а не обязательно в `~/.claude`.** Проверить переменную (`echo $CLAUDE_CONFIG_DIR`) **прежде** чем идти в файловую систему. Пустой `~/.claude/plugins/` при успешной установке читается как «не сработало», хотя сработало.
- **Верифицировать состоянием, а не файлами:** `claude plugin list` (статус, версия, scope), `claude plugin marketplace list`. Команда знает, где её состояние; догадка о путях — нет.
- `claude plugin details <name>` — инвентарь компонентов и **стоимость в токенах**: `always-on` платится каждой сессией, `on-invoke` — каждой активацией. Назвать владельцу обе цифры: скилл, который стоит контекста в каждой сессии, должен эту цену отрабатывать.
- Плагин подхватывается **со следующей сессии**, не в текущей. Нужен эффект сразу — прочитать `SKILL.md` напрямую и применить вручную, но слэш-команд при этом всё равно нет; сказать об этом.
- **Установка ≠ включённость:** `claude plugin disable|enable <name>` — держать поставленным и выключенным законно.
- **Если профили агента разведены** (личный и рабочий): они разведены целым каталогом конфигурации, а не настройкой. Поставленное в одном профиле в другом **не видно вообще** — изоляция уже есть. Обратная сторона: нужное в обоих ставится дважды.

## Шаг 6. Обновление и откат

```sh
claude plugin marketplace update [name]   # без имени — все
claude plugin update <plugin>             # требует перезапуска сессии
claude plugin uninstall <plugin>
claude plugin marketplace remove <name>
```

Автообновления нет — это ручной жест. Обратная сторона приятная: ничего не меняется за твоей спиной.

**Каталог гарнитуры руками не трогать.** `$CLAUDE_CONFIG_DIR/plugins/marketplaces/<name>` — git-клон, которым распоряжается гарнитура. `git pull` в нём выглядит безобидно, но `marketplace update` после него не находит, что забрать, и пропускает и отметку в реестре, и наполнение `plugins/cache/`. Манифест читать из рабочего клона в `.repos/`; состояние двигать только командами `plugin`.

**Включён ≠ загружен.** Плагин может стоять в `enabledPlugins` без каталога в `plugins/cache/<marketplace>/<plugin>/` — тогда скилла нет, а команда состояния из шага 5 всё равно докладывает «включён». Здесь файловый слой отвечает на вопрос, на который команда не отвечает: нет каталога версии — не загружено. Выход — `plugin install <plugin>@<marketplace>`, он наполняет кэш, не сверяясь с git.

**Обновлён ≠ перезагружен, и это отказ хуже предыдущего.** Кэш ключуется каталогом **версии**: `plugins/cache/<marketplace>/<plugin>/<version>/`. `marketplace update` подтягивает клон и докладывает успех, но существующий каталог версии не перенаполняет. Правка, уехавшая под неизменной версией, не исполняется — а видно только то, что обновление прошло.

Отсюда два следствия. **Свой плагин:** `version` в манифесте двигается тем же изменением, что и содержимое, иначе развёртывание молча остаётся на старом. **Чужой плагин:** после `marketplace update` версию сверять файловым слоем, а не отчётом команды — `diff` каталога кэша против клона отвечает на этот вопрос, отчёт не отвечает.

Наблюдалось на своём плагине: смерженные изменения не были в силе, кэш стоял на прежней установке, и исполнялся старый хук — с тем самым дефектом, который правка уже снимала.

**Загружен ≠ привязан в этой сессии, и слои разъезжаются по-разному.** После поднятой версии кэш наполняется, и **скилл** новую версию отдаёт сразу — его описание в перечне меняется в той же сессии. **Хук** — нет: он остаётся привязан к каталогу той версии, что была на старте сессии, и продолжает исполнять её файл. Перечень скиллов показывает новое, рубеж работает старым, и оба отчёта об установке при этом успешны.

Вопрос решается поведением, а не каталогом: наличие `plugins/cache/<plugin>/<новая версия>/` доказывает наполнение, но не привязку. Нужен **различитель** — вызов, который старая и новая версии обрабатывают по-разному, запущенный там, где пропуск безвреден (вне git-репозитория, с заведомо отсутствующим файлом). Отказ или его отсутствие и есть ответ.

Перепривязка хука наблюдением не проверена: новая сессия — первое, что стоит попробовать, но это предположение, а не установленный факт.

## Шаг 7. Зафиксировать

Поставили нативно и на пробу — фиксировать нечего, откат в одну команду.

Решение оставить — особенно с вето-признаками из шага 2, со сменой дома или с правкой `settings.json` — это уже архитектурное решение: `/archgate`, при прохождении ADR в `80-kernel/stele/`. Свой скилл заведён или изменён — обновить каталог `80-kernel/docs/skills.md` (обзор, не дубль логики).
