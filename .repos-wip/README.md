# .repos-wip — что сейчас в работе

Рабочие деревья (`git worktree`) поверх клонов из `.repos/`. **Содержимое вне git этого vault** (`.gitignore`) — как и у клонов: у каждого дерева свои коммиты и свой remote.

Трекается только этот файл.

## Зачем отдельный каталог

Разделены две разные вещи, которые до этого лежали вперемешку.

`.repos/` — **отражение стержневых веток**: клоны сидят на дефолтной ветке, только пуллятся и служат источником. Ничего своего там не коммитится.

`.repos-wip/` — **список того, что в работе**. Каталог читается как ответ на вопрос «чем я сейчас занят»: одна строка `ls` — один тикет. Пустой каталог означает, что незакрытой работы нет, и это утверждение, а не догадка.

## Раскладка

Плоско, без групп — их роль уже сыграна в `.repos/`, а здесь важна обозримость списка:

```
.repos-wip/
  <repo>-<ticket>
```

Имя каталога — репозиторий и тикет, потому что одна задача часто идёт сразу в нескольких репозиториях, и различать их надо с одного взгляда.

## Правила

- Дерево ставится на **уже существующую** ветку, если её заводит автоматика трекера, — своей ветки под задачу тогда не создаём. Команды — в разделе ниже; конвенции конкретного работодателя — в заметке о порядке работы с его репозиториями (`30-knowledge/`).
- Переносить дерево только `git worktree move`; после `mv` оно остаётся рабочим, но помечается `prunable` и умирает от первого `git worktree prune`.
- По закрытии тикета — `git worktree remove` и `git worktree prune`. Дерево есть расходные леса: то, что здесь задержалось, либо не закрыто, либо забыто.
- В `.vscode/settings.json` деревья **не регистрируются и не должны**: каталог обходится автодетектом (глубина 2, ignore родителя детекту не помеха), поэтому worktree появляется в панели Source Control при заведении и исчезает при сносе. Панель показывает то же, что и `ls` здесь.

## Команды

Всё ниже запускается **из корня vault**. Две переменные задают задачу целиком:

```bash
CLONE=.repos/<group>/<repo>
TREE="$PWD/.repos-wip/<repo>-<ticket>"   # абсолютный — см. ниже
```

Путь к дереву абсолютный не для красоты: при `git -C` относительный путь считается **от клона**, а глубина клонов разная (`<group>/<repo>` против `<group>/<subgroup>/<repo>`), так что `../../../` верен через раз. `$PWD` раскрывается шеллом до корня vault и от глубины не зависит.

### Ветка автоматики уже есть

```bash
git -C "$CLONE" fetch --prune
git -C "$CLONE" worktree add "$TREE" <bot-branch>
```

Без `-b`: ветка существует, флаг создал бы вторую того же имени с другой историей.

Есть ли она — проверяется по MR/PR в целевом репозитории (`glab mr list -R <group>/<repo> --search "<TICKET>"`, `gh pr list --search`). Вывод «ветки нет» требует свежего `fetch --prune` и взгляда не только на открытые MR/PR.

### Ветки ещё нет

```bash
git -C "$CLONE" fetch --prune
git -C "$CLONE" worktree add "$TREE" -b <ticket> --no-track origin/<target>
```

**База — `origin/<target>` явным аргументом, не HEAD клона.** Таргет выбирается по линии работы, а не по тому, на чём стоит клон: у репозитория может быть отдельная ветка под окружение или под релизную линию, и ветка, ответвлённая не от той, есть выброшенная работа.

**`--no-track`.** Иначе upstream станет `origin/<target>`: `status -sb` начнёт считать ahead/behind относительно чужой ветки, а `pull` втянет её в работу. До появления апстримной ветки upstream'а у локальной нет.

**Имя — голый тикет строчными** (`<ticket>`). Ветка автоматики обычно длиннее — `<ticket>-<slug>` с возможным суффиксом таргета, — поэтому форма имени сама говорит, что это ещё не она. Каталог дерева переименования не потребует: он назван по репозиторию и тикету, а не по ветке.

### Ветка появилась — усыновляем

Из каталога дерева:

```bash
git fetch --prune
git branch -m <bot-branch>            # работает и на ветке, занятой worktree
git rebase origin/<bot-branch>
git push -u origin HEAD
```

**Переименование, а не `push origin HEAD:refs/heads/<bot-branch>` с `--set-upstream-to`.** Второе короче ровно один раз, а дальше расхождение имён ломает каждый следующий `push`: при `push.default=simple` git отказывается словами «The upstream branch of your current branch does not match the name of your current branch».

**Rebase обязателен, а не «если не пройдёт».** Автоматика ответвляет от текущего состояния таргета, а не от твоей базы, и за время работы таргет уезжает — `push` без перебазирования не проходит fast-forward.

### Своя ветка в апстрим

`git push -u origin HEAD` — и всё. Но в репозитории, где ветки заводит автоматика трекера, это ровно тот дубль, против которого написана конвенция: законных поводов два — репозиторий без автоматики либо осознанное решение, что тикета под это не будет. Повод «бот тормозит» — не третий, а отложенное усыновление.
