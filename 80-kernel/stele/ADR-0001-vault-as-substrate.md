# ADR-0001 — Vault как единственный субстрат

## Контекст

Рабочее знание инженера расползается по трём-четырём поверхностям: тикеты в трекере, страницы в корпоративной вики, локальные заметки, история чатов с агентом. Ни одна из них не переживает смену инструмента, и ни одна не даёт агенту читаемого состояния. Нужен один носитель, который агент правит напрямую и который восстановим из клона.

## Решение

**Единственный субстрат — каталог markdown-файлов под git**, открываемый Obsidian и правимый агентом напрямую. Всё состояние системы (карточки задач, проекты, планы, память, знание) есть файлы в этом дереве.

- Агент пишет md напрямую (INV-4), без прослойки-MCP к Obsidian.
- Внешние сервисы (трекер, вики, CI) остаются system of record по **своему** предмету; vault хранит **ссылки** на них и собственную рабочую канву, не копию их состояния (INV-2).
- Переносимость проверяется буквально: `git clone` + Obsidian + агент = рабочая система (INV-1).

## Альтернативы

- **База данных / SaaS для заметок** — отклонён: ломает INV-1 (состояние не в файлах), требует рантайма (INV-7), агент не правит напрямую.
- **Вики работодателя как основной носитель** — отклонён: не переживает смену работодателя, недоступен офлайн, агент не имеет надёжного write-доступа. Вики остаётся **выходом** для того, что адресовано коллегам.
- **Только тикеты трекера** — отклонён: трекер хранит состояние deliverable, но не рабочую канву («что пробовал, где застрял, с чего начать завтра») — а теряется именно она.

## Последствия

- **+** Одна поверхность, переносимая и грепаемая; агент и инженер правят один и тот же объект.
- **+** История решений и работы versioned из коробки.
- **−** Дисциплина синхронизации с трекером — на инженере: vault не узнаёт о смене статуса тикета сам.
- **−** Markdown не даёт реляционных запросов; агрегация ограничена тем, что умеют dataview / Bases.
